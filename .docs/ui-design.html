UI design proposals

Matillion Diff · draft · 2026-10-05 · Companion document: Architecture draft

Five layout concepts for a read-only, visual diff viewer for Matillion ETL repositories. The first release targets Matillion ETL for Azure Synapse, and the designs leave room for other Matillion ETL variants. All of them use the same example: the branch feature/eu-orders compared against main. In that branch the orchestration job daily_load lost a truncate step, had its load component renamed and its SQL changed, and gained a step that logs load failures. The mockups are interactive, so try clicking on them.

Design principles

Speak Matillion, not JSONShow component names, types and parameter labels. Slot numbers and internal IDs appear only in the Raw view.
Signal over noiseLayout-only changes are hidden by default and one toggle away. Badge counts show semantic changes only.
One selection, many lensesSelecting a component in any view selects it in every view. Switching views never loses your place.
Visibly read-onlyA permanent "read-only" marker, and no buttons that suggest editing. No save, apply, revert or merge.
Never colour aloneEvery change kind has a glyph and a label as well as a colour, and removed items also get a dashed outline. This keeps the UI usable for red-green colour blindness.
Keyboard firstReviewers move through changes with j/k and through objects with [/], without touching the mouse.

Shared design language

Change kinds

+Added
Only in compare. Solid, thick outline.
−Removed
Only in base. Dashed outline, shown as a ghost on the canvas.
~Modified
Parameter, SQL, grid or variable content changed.
→Renamed
Same component (matched by ID), new name.
⇄Rewired
Incoming or outgoing connectors changed.
↔Layout
Only position or size changed. Hidden by default.

Connectors

Matillion's own canvas colours connectors green for success and red for failure, which clashes with the diff colours. In Matillion Diff, colour always means change status. The connector kind is shown by a small glyph at the middle of the edge instead: ✓ success, ✗ failure, → unconditional, T/F true/false, ⟳ iteration.

Matillion ETL variant

Each opened repository has a Matillion ETL variant, picked when the repository is opened. In the first release the only variant is Synapse. The variant is shown as a chip next to the repository name in every view (Synapse). It controls which component types are known, how SQL is highlighted (T-SQL for Synapse), and the list in the component-type filter.

⚠ not on Synapse
The component type exists in Matillion ETL but not in the selected variant. This usually means the job was copied from another variant. Diffing is unaffected.
?Unknown type

Component categories

Components carry a thin left strip in their category colour, so they are recognisable without one icon per component type. The categories group the 65 types in implementation_id_to_type.json, following the order of Matillion's component palette. That map is shared by all variants. Types that the selected variant does not offer are left out of the component-type filter. Category colour is secondary: change status is always shown by the outline, the glyph and the label, never by the strip.

AWorkbench

An IDE-style, three-pane layout: changed objects on the left, a structured diff in the middle, an inspector on the right.

This layout is familiar to anyone who has used VS Code or a Git client. The middle pane shows a component → parameter table with base and compare columns. The inspector shows detail for the selected row, such as a SQL diff or grid table. The middle pane's tabs switch between lenses (Summary, Structure, Canvas, JSON, Raw) over the same diff.

BCanvas diff

The job is drawn as Matillion users already picture it, with change status layered on the canvas.

The canvas is the main view. Four modes: Side by side (base and compare in synchronised viewports), Overlay (one canvas, with removed components as ghosts and moved components showing their old outline), and Before or After on their own. Clicking a component opens a drawer with its parameter changes.

Strengths

  • Instantly readable for Matillion users
  • Rewiring and flow changes are obvious
  • Good for walking non-developers through a change

Weaknesses

  • Parameter detail needs the drawer
  • Highest build effort (layout, hit-testing, zoom)
  • Transformation jobs with more than 100 components get crowded

Best for

  • Understanding what the job does differently
  • Demos and change-approval meetings

CReview feed

A pull-request-style, single-column list of readable change sentences, grouped by object.

Each semantic change becomes one card: "Renamed Load Orders to Load Orders (EU)". Expanding a card shows the evidence (a SQL diff, a grid table, the connectors involved). Objects can be ticked as reviewed. That progress is kept for the session only and is never written to the repository. This layout also works well on narrow windows and in a browser.

DTime machine

The history of one job as a change matrix: components down the side, commits across the top.

The question here is not "what differs between A and B" but "how did this job evolve, and when did this component change?". Click a commit to see it against its parent, or Shift-click a second commit to select a range. The range then drives the other views.

Strengths

  • Unique "blame for components" insight
  • Shows hot spots and churn
  • Makes range selection visual instead of typing SHAs

Weaknesses

  • Has to diff every commit pair, which is costly the first time
  • Only one object at a time

Best for

  • Investigating a regression
  • Auditing who changed what, and when

ECanonical JSON diff

A familiar line-by-line code diff, run on a cleaned-up rewrite of the job JSON instead of the raw export.

The job stays JSON, but it is rewritten into a canonical form. Slot maps become named keys. Components and connectors are referenced by name instead of ID. Layout and derived ID arrays are dropped. SQL becomes an array of lines. Components are ordered by component ID, so a rename doesn't move a block. A standard split or unified diff of that JSON is surprisingly readable. This is the cheapest proposal to build, and the same printer can later be a git textconv driver.

Lines that differ only by a trailing comma (for example after an element is appended) are treated as unchanged.

Strengths

  • Smallest build effort, and a good MVP fallback
  • Familiar to developers
  • Reusable outside the app via textconv

Weaknesses

  • Still a line diff: rewiring and renames are only implied
  • Needs comma-insensitive line matching
  • Can't hide layout-only changes per item

Best for

  • Developers who live in diffs
  • Copying and pasting into tickets

The proposals don't compete. They are lenses on the same JobDiff, which the architecture computes once and shares.

Recommendation: combine them

Use A (Workbench) as the application shell, and show the other proposals as tabs over the selected object. Make C (Review feed) the default tab, because most people first want to know what changed in plain words. D (Time machine) opens from any object's context menu.

Open UI questions

  • Where is the variant picked? This proposal puts it in the open-repository dialog, preselected to Synapse, and makes it changeable in the repository settings.
  • Should the canvas use real Matillion component icons? There are licensing and maintenance concerns, so category strips are proposed instead.
  • Should "Reviewed" marks be kept between sessions in app-local storage, keyed by object path and compare SHA? They would still never go into the repository.
  • Should the canvas follow Matillion's coordinates exactly, or tidy them automatically? This proposal keeps the original coordinates so the canvas matches what users see in Matillion.
