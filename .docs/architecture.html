Matillion Diff: a read-only visual diff for Matillion ETL repositories

Architecture draft · Flutter · 2026-10-05 · Companion document: UI design proposals

Matillion ETL stores every job as a deeply nested JSON document. Ordinary diff tools compare those files line by line, so a one-word change to a component turns into a wall of brace and slot noise. Matillion Diff reads a Git repository, parses the Matillion objects into a proper domain model, and shows what changed in the job (components, parameters, connections, variables) rather than what changed in the text. It never writes to the repository.

Scope: Matillion ETL for Azure Synapse first. The first release supports Matillion ETL for Azure Synapse only. Everything that differs between Matillion ETL variants (which component types exist, their parameters, the SQL dialect) is kept in data files, so that other variants such as Snowflake, Redshift, BigQuery or Delta Lake on Databricks can be added later without changing the parser or the diff engine. See Matillion ETL variants.

Goals & scope

Goals

  • Semantic diffs. Compare two revisions of a Matillion job as a job: added, removed, renamed and modified components, changed parameter values, rewired connectors, changed variables and notes.
  • Visual diffs. Show the change on a canvas that looks like the Matillion job canvas, with change status layered on top.
  • Noise suppression. Separate meaningful changes from cosmetic ones (canvas coordinates, map ordering, internal ID churn) and hide the cosmetic ones by default.
  • Repository navigation. Pick any two revisions (branch, tag, commit, working tree), see which Matillion objects changed, and browse the history of a single job.
  • Strictly read-only. The app cannot modify the repository, and the code is built so that it has no way to.
  • Synapse now, other variants later. Support Matillion ETL for Azure Synapse in the first release, and add other Matillion ETL variants by adding a variant profile, not by changing code.

Non-goals

  • Editing, merging, resolving conflicts, committing, pushing, or creating branches or tags.
  • Running or validating jobs, or connecting to a Matillion instance.
  • Replacing a general Git client. Non-Matillion files appear only as plain text diffs.

Line diffs fail on Matillion JSON for structural reasons:

  • Slot maps. Parameters, elements and values are objects keyed by slot numbers ("1", "2", …). The meaningful key (the parameter name) sits several levels deeper than the change.
  • Opaque identifiers. Components are keyed by numeric IDs and typed by implementationID hashes. Connectors refer to components by ID only.
  • Layout noise. Moving a component changes x, y, width and height, which buries real changes.
  • Embedded code. SQL and Python sit inside JSON strings with escaped newlines, so a one-line SQL edit shows up as one huge changed line.
  • Grids. Grid parameters such as column mappings are nested row/column slot maps. Inserting one row shifts every slot that follows it.

Repository assumptions

Verify against a real repository before implementation. The object format below is the Matillion ETL job export format as it is generally understood. The exact folder layout written by Matillion's Git integration, and the full set of object types, need to be confirmed against a sample repository. The design deliberately does not depend on file paths: objects are recognised by sniffing their content.

Detection rule: a .json file is a Matillion job if its root has info.type in {ORCHESTRATION, TRANSFORMATION} and a job.components object. Further object kinds (environments, project variables, schedules, shared jobs) get their own ObjectAdapter once samples are available. Anything else falls back to a generic, key-sorted JSON tree diff.

Non-functional

  • Read-only: no code path in the app can change refs, objects, the index, the working tree or the remote. See §7.
  • Performance: a 300-component job is parsed and diffed in under 200 ms on a mid-range laptop, and the UI never blocks.
  • Offline: local repositories work with no network.
  • Platforms: Windows, macOS and Linux desktop first. Web later (F11).
  • Extensibility: adding a Matillion ETL variant means adding a profile file and test fixtures. The parser, the diff engine and the UI stay unchanged.
  • Safety with untrusted repositories: opening a repository never executes repository-supplied code (hooks, fsmonitor, external diff drivers, textconv).

Architecture overview

A layered (ports-and-adapters) design. The domain, which covers the Matillion model and the diff engine, is pure Dart with no Flutter or I/O dependencies. Infrastructure plugs in behind read-only ports, and the Flutter UI only talks to application use cases.

The read-only guarantee

"View only" is the core product promise, so it is enforced in several independent layers. If one layer has a bug, the others still hold.

  1. Port design, enforced at compile time. RepositorySource exposes only query methods. There is no commit, checkout or push, so the UI and use cases have nothing to call.
  2. Command allowlist, enforced at run time. Every Git invocation goes through ReadOnlyGit, which accepts only an explicit set of read-only subcommands and flags and throws ReadOnlyViolation for anything else. A unit test fails the build if the allowlist grows without review.
  3. No lock or index writes. Every call runs with --no-optional-locks and GIT_OPTIONAL_LOCKS=0, so even status-like reads do not refresh .git/index.
  4. No repository-controlled execution. The wrapper passes -c core.fsmonitor=false -c core.hooksPath=<empty dir> -c protocol.file.allow=never and uses --no-ext-diff --no-textconv. Opening an untrusted repository therefore runs no code from that repository.
  5. Remote mode clones into an app-owned cache. Remote URLs are mirrored into the app's cache directory (clone --mirror --filter=blob:none, later fetch). The mirror's remote.origin.pushurl is set to an invalid value, so a push would fail even if one were attempted. The user's own clones are never fetched into. They are read as they are.
  6. Least-privilege tokens (v2). Hosted adapters ask only for read scopes (GitHub "Contents: read-only", GitLab read_repository, Azure DevOps "Code (Read)", Bitbucket repository:read). An HTTP interceptor rejects every method except GET and HEAD.
  7. The working tree is read, never written. Working-tree files are opened read-only with File.readAsBytes. The app has no file-writing code path into the repository folder.
final class ReadOnlyGit {
  ReadOnlyGit(this.repoDir, {required this.gitExe});

  static const _allowed = {
    'rev-parse', 'for-each-ref', 'log', 'rev-list', 'merge-base',
    'diff-tree', 'ls-tree', 'cat-file', 'show', 'status',
  };
  static const _hardening = [
    '--no-optional-locks',
    '-c', 'core.fsmonitor=false',
    '-c', 'core.hooksPath=/nonexistent',
    '-c', 'protocol.file.allow=never',
  ];

  Future<ProcessResult> run(String sub, List<String> args) {
    if (!_allowed.contains(sub)) throw ReadOnlyViolation(sub);
    return Process.run(gitExe, [..._hardening, sub, ...args],
        workingDirectory: repoDir,
        environment: {'GIT_OPTIONAL_LOCKS': '0', 'GIT_TERMINAL_PROMPT': '0'});
  }
}

Repository access layer

The domain defines one read-only port. Every adapter implements it, so the UI cannot tell a local clone from GitHub.

abstract interface class RepositorySource {
  Future<RepoInfo> info();
  Future<List<RefInfo>> refs();                                   // branches + tags
  Future<List<CommitInfo>> log({Rev? from, String? path, int limit = 200});
  Future<List<ChangedPath>> changedPaths(Rev base, Rev compare);  // incl. renames
  Future<BlobRef?> resolve(Rev rev, String path);                 // path → blob SHA
  Future<Uint8List> readBlob(BlobRef blob);
}

final class CommitRev extends Rev { final String sha; ... }
final class RefRev    extends Rev { final String name; ... }   // resolved to a SHA once, then pinned
final class WorkingTreeRev extends Rev {}                       // local source only

Matillion object model & normalization

Parsing turns raw JSON into a normalized model: slot maps become ordered lists keyed by meaningful names, IDs resolve to components, and cosmetic data is kept apart from semantic data. Every later step works on this model. 

final class MJob {
  final String name;
  final JobType type;                        // orchestration | transformation
  final String? description;
  final Map<ComponentId, MComponent> components;
  final List<MConnector> connectors;
  final List<MVariable> variables;           // job variables
  final List<MGridVariable> grids;           // grid variables
  final List<MNote> notes;
}

final class MComponent {
  final ComponentId id;
  final ComponentType type;                   // resolved from implementationID via the variant registry
  final String name;                         // lifted out of the "Name" parameter
  final List<MParameter> parameters;         // ordered by slot, keyed by name
  final Layout layout;                        // x, y, w, h: cosmetic
}

final class MParameter { final int slot; final String name; final MValue value; }

sealed class MValue {}
final class MScalar extends MValue { final String type; final String value; }  // STRING, INTEGER, …
final class MText   extends MValue { final String text; final Language lang; } // SQL / Python / Bash
final class MList   extends MValue { final List<MScalar> items; }
final class MGrid   extends MValue { final List<String> columns; final List<List<MScalar>> rows; }

final class MConnector {
  final ConnectorKind kind;                  // success | failure | unconditional | true | false | iteration
  final ComponentId source, target;
}

Normalization rules

  • Slots to structure. parameters[slot].elements[row].values[col] becomes a scalar, a list or a grid, based on the shape and on a hint from the component type registry.
  • Component type registry. Resolves implementationID to a type name, a category and diff hints. See below.
  • Language detection. A parameter becomes MText if the registry says so, or as a fallback if it contains newlines and is longer than about 80 characters.
  • Edge model. The six connector maps merge into one edge list with a kind. The per-component *ConnectorIDs arrays are dropped because they are derived data.
  • Stable ordering. Components are ordered by component ID, so a rename never moves a component. Parameters are ordered by slot, and variables and grid variables by name. Printing is therefore deterministic, which makes CanonicalJsonPrinter output safe to line-diff.
  • Lossless escape hatch. Every model node keeps a pointer to its raw JSON subtree, so the "raw" view can show exactly what the file says.

Component type registry

The registry is seeded from .docs/implementation_id_to_type.json, which maps 65 implementationID values to type names (all IDs and all names are unique). This map is shared by all Matillion ETL variants. Not every type in it exists on every variant, and some do not exist on Synapse. Which types a variant offers is defined by its variant profile. The IDs are signed 32-bit integers stored as string keys, such as "-741198691": "Database Query". The parser reads implementationID as a JSON number and looks it up by its decimal string.

The file contains names only, so the registry has two assets. The ID map is kept exactly as provided, so it can be replaced or regenerated from new exports without touching anything else. Presentation and diff hints live in a second, hand-maintained file that is keyed by type name:

{
  "Database Query": { "category": "read",   "code": { "SQL Query": "sql" } },

Choosing the variant

  • The variant is chosen per repository when the repository is opened, and stored in app-local settings, never in the repository. In the first release, Synapse is the only option and is preselected.
  • Automatic detection is only added if the exported JSON turns out to contain a reliable marker for the variant. This is an open question for the sample repository.
  • Each parsed job is cached under (blob SHA, variant id), because the variant affects normalization (code and grid hints).

Behaviour for components outside the variant

If a job contains a type that is in the shared map but not in the Synapse profile, the component is shown with its name and a "not available on Synapse" warning. This usually means the job was copied from another variant. Diffing is unaffected. IDs that are in no map at all are handled as unknown types (see Component type registry).

Adding a variant later

  1. Add assets/registry/variants/<variant>.json, listing its components and any extra types or parameter overrides.
  2. Add a fixture set exported from that variant under test/fixtures/<variant>/.
  3. Add syntax highlighting for its SQL dialect if it is new.
  4. Run the registry consistency tests. No changes are needed in the parser, the diff engine or the UI.

Semantic diff engine

The matillion_diff package takes two MJob values and returns a JobDiff tree. It runs in three stages.

1 · Match

The matcher pairs components across the two versions:

  1. By ID. Matillion keeps component IDs stable while a component exists, so this resolves most components.
  2. By type and name for the components left over. This catches delete-and-recreate.
  3. By similarity for what is still left: same type, and a parameter-overlap score above a threshold. This catches copy-paste-and-rename.

Connectors are matched on (kind, matched source, matched target), never on connector ID, so ID churn alone produces no diff.

2 · Compare

  • Parameters are compared by name. Scalars use equality. MText gets a line diff (Myers, with word-level highlighting within changed lines).
  • Grids are compared row by row. Rows are matched on a key column from the registry (for example the target column name) and otherwise by LCS over whole rows. Cells are then compared within each matched row.
  • Variables and grid variables are matched by name. Notes are matched by ID first, then by text similarity.

Data flow: opening a job diff

Revisions are resolved to commit SHAs once, when the user picks them. From then on every read is content-addressed, so cache entries never go stale and a moving branch never shows a half-updated state.

Performance & caching

  • Content-addressed caches. Parsed MJob values are cached by blob SHA and JobDiff values by (shaA, shaB), both in an in-memory LRU. Git blobs never change, so nothing needs invalidating.
  • Isolates. Parsing, normalizing and diffing run in Isolate.run. Large repositories are pre-scanned for the changed-objects list with a bounded pool of about four concurrent isolates.
  • Batch blob reads. One persistent git cat-file --batch process per repository streams blobs without per-file process start-up (which is slow on Windows).
  • Cheap list stats. The changed-objects list first shows Git's name-status. Semantic badge counts fill in progressively as each diff finishes, and objects whose only changes are layout get a grey badge.
  • Virtualized rendering. Trees and text views use slivers. The canvas paints only what is visible and caches component glyphs with Picture.

Error handling

SituationBehaviour
Git not installed or too oldBlocking onboarding screen with install instructions. No partial functionality.
Invalid JSON in one revisionThat side falls back to a plain text diff, with a banner saying "Could not parse base revision: line 412, unexpected token".
Unknown object kindGeneric key-sorted JSON tree diff.
Unknown component typeRendered as a generic component. Diffed normally. Listed in Settings → "Unknown component types" so the registry can be extended.
Component type not available in the selected variantShown with its name and a "not available on Synapse" warning. Diffed normally.
Very large file (> 20 MB)Asks for confirmation before parsing.
Auth failure on mirror fetchShows Git's stderr and keeps using the last mirrored state, marked "stale".
ReadOnlyViolationTreated as a bug: logged, an error dialog is shown, and nothing is executed.

Testing strategy

  • Fixture pairs. test/fixtures/<variant>/<case>/{base,compare}.json plus an expected.txt golden of the diff in printed form. Cases include rename, delete-and-recreate, grid row inserted, SQL edit, layout-only, connector rewire, and ID renumbering with no semantic change (which must produce an empty diff).
  • Registry tests. Every ID in a variant profile exists in the shared map or in the profile's extraTypes. Every meta override names a type the variant offers.
  • Property tests. diff(x, x) is empty. diff(a, b) mirrors diff(b, a). Shuffling map order or renumbering IDs does not change the result.
  • Read-only tests. Every RepositorySource method runs against a temporary repository, and afterwards the test asserts that .git is byte-identical (refs, index, objects, config). An allowlist snapshot test fails when a subcommand is added.
  • Widget and golden tests for badges, tree rows and canvas rendering in light and dark themes.
  • Integration test on all three desktop platforms in CI against a small sample Matillion ETL for Synapse repository.

Risks & open questions

Exact repository format
Which files does Matillion's Git integration write, and in which folders? Are there non-job objects (environments, project variables, schedules, API profiles) that need adapters? Action: get an anonymized sample repository before the MVP starts.
Component type mapping
implementationID values are not formally documented. implementation_id_to_type.json now covers 65 types (see Component type registry). The map is shared across variants, and some of its types do not exist on Synapse. Still open: exactly which of the 65 types the Synapse profile lists, whether any Synapse-only components are missing from the map, and whether IDs are the same across Matillion ETL versions. Mitigation: generic fallback rendering, plus a list of unknown IDs found in the opened repository, which can be added to the map.
Variant detection and differences
It is not yet known whether exported job JSON says which variant it came from, or how much the parameters of the same component type differ between variants. Action: check the Synapse sample repository for a variant marker. Before the first non-Synapse variant is added, compare the same job exported from two variants.
Component ID stability
Matching assumes that IDs survive edits. If Matillion re-numbers components on import or export, the type-and-name and similarity matchers take over. Fixtures must cover this case.
Git on users' machines
Depending on a system git is the pragmatic choice, but locked-down corporate laptops may not have it. A bundled portable Git for Windows is an option, at the cost of a larger installer.
Hosted API rate limits (v2)
Comparing large branches through REST can hit rate limits. Use the tree and compare endpoints rather than fetching file by file, and reuse the content-addressed cache.
Canvas fidelity
The canvas is a recognisable approximation of Matillion's canvas, not a pixel-perfect clone. Icons for every component type are out of scope at first; components are shown by category colour and initials.
